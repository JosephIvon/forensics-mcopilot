## 3.1 概念：门禁不是绿灯收集器

CI 里最常见的自欺，是把"检查全绿"当成"质量合格"。一个永远绿的检查等于没有检查——
它只证明你的代码能通过检查，不证明检查能拦住任何东西。

本章的核心命题只有一句：

> **门禁的价值不在"能过"，在"能拦"。未经验出力的门禁，是装饰。**

由此推出三条工程纪律，本章的真实工件将逐条兑现它们：

1. **每条门禁必须配负向测试**——注入已知缺陷，证明它真的会 FAIL；
2. **负向注入必须自证生效**——"注入没打中"绝不允许静默当成 PASS；
3. **检查自己的检查**——注入器本身也要被门禁约束。

## 3.2 十二道门禁：按"它防什么"分层

`scripts/gate_protocol.ps1` 用一个 `Add-Gate` 注册表维护十二道门（G1-G12），每门
独立超时（默认 300s）、**独立退出码域（10-21）**，支持 `-Only` 子集运行。
分层看比逐条背更清楚：

| 层 | 门 | 防什么 | 硬数字 |
|---|---|---|---|
| 生成正确性 | G1 | csc 直编客户端+契约源零错误 | — |
| 行为契约 | G2 | 黄金帧测试 | 30 条 |
| 行为契约 | G3 | TCP 契约三阶段 + 异常码扫掠 | 18+1 条 |
| 行为契约 | G4 | RTU 行为契约 + 超时契约（收帧不回桩） | 11+1 条 |
| 外部锚定 | G5 | quote 反查：文档引用页码逐条对官方 PDF | 53/53 |
| 回归网络 | G6 | pytest 协议域子集 | 4 文件 |
| 外部锚定 | G7 | 外部真值锚点：sha256 + 再提取抽查 + URL 告警 | 14 锚点 |
| 文档真实性 | G8 | 文档一致性：数字全部从代码/知识库实算对账 | — |
| 扩展协议 | G9 | SLMP 契约 | C1-C9 |
| 行为闭环 | G10 | 接入闭环三场景：全绿/已知归因/未知升级 | — |
| 对抗验证 | G11 | 故障农场：批产→检出→判卷→矩阵→**N1 错标必红** | — |
| 真实分布 | G12 | 真实语料逐行断言 + 负向三重 → 全量检出判卷 | Lemay 夹具 |

三个设计点值得停下：

- **独立退出码域**：G5 挂了报 14，G9 挂了报 18——机器可读的失败定位，CI 日志不用
  人肉翻。
- **G8 的"实算对账"**：文档里每个数字都从代码/知识库现算再对——文档腐烂在多数
  项目里无人检测，这里它是被门禁看管的。
- **G11/G12 的"负向必红"**：连门禁自己的判卷器都被要求"错标必须变红"——对抗
  思维贯穿到第三层。

## 3.4 动手二：负向测试现场课——注入一个缺陷，看门禁咬人

`scripts/gate_negative.ps1` 是本章真正的明星。它对关键门**注入已知缺陷**，要求
对应门必须变红。四条用例 + 一条元用例：

| 用例 | 注入（只注入 `out/gates/negative/` 下的**副本**） | 要求变红的门 |
|---|---|---|
| N1 | `modbus.json` 副本某条 `spec_ref.quote` 换成编造文本 | G5 quote 反查 |
| N2 | `ModbusTcpClient.cs` 副本 `MaxBitResponseBytes` 从 250 退回 245 | G2 黄金帧 |
| N3 | `capability_matrix.json` 副本 `stats.s7.entries` 181→180 | G8 实算对账 |
| N4 | README 副本"黄金测试（30 条"改成"31 条" | G8 文档一致性 |
| **META** | **故意不命中的注入点** → 注入器必须退出码 3 | **注入器自己** |

四条结构规则，每条都值得抄走：

1. **副本注入，零接触 tracked 文件**——负向测试永远不污染真实资产；
2. **阳性对照**：每个注入用例同时跑"未注入副本"，必须 PASS——证明失败来自
   注入，而不是副本路径本身有问题；
3. **注入必须自证生效**（铁律3）：替换计数 ≥1、注入后内容 ≠ 原内容、文件含探针
   标记，任一不满足 → 退出码 3"注入点未命中"——**打偏的枪绝不允许记成命中**；
4. **META 用例**：注入器自己被一条"故意打偏"的用例看管——检查自己的检查。

N2 有个动人的细节：`250 = ceil(2000/8)` 是当年 P1-1 缺陷的真实修复值，负向测试
把它退回 245，等于**让历史缺陷原地复活一次**来证明门禁在场。修复不是终点，
"修复可被复检"才是。

## 3.6 退出码语义（机器可读的失败学）

`gate_negative.ps1` 的退出码表本身就是一份微型设计文档：

| 码 | 含义 |
|---|---|
| 0 | 检测力矩阵全 PASS |
| 1 | 有用例未达预期（门没红 / 阳性对照没绿） |
| 3 | 任一注入点未命中（打偏≠命中） |
| 100 | 未捕获异常（trap 兜底） |

注意 1 和 3 的区别：门没红是**被测方**失败，打偏是**测试器**失败——两者必须
可区分，否则测试器的 bug 会伪装成"质量没问题"。

## 3.7 习题

**知识题**

1. 为什么"阳性对照"必须存在？删掉它，负向测试的哪个结论失去支撑？
2. N2 为什么选 P1-1 的真实修复值来注入，而不是随便改一个常数？
3. 退出码 1 和 3 的区分，防的是哪一类系统性自欺？

**反事实题**（参考答案=真实裁决，含代价）

4. 删掉 `gate_negative.ps1`，哪类回归会漏进主干？
   *参考*：至少 N1-N4 覆盖的四类——编造引用、回退修复值（P1-1 类）、统计数字
   漂移、文档数字腐烂。且"门禁自身失效"将不可见（META 用例消失）。
5. 你要给自己的项目立第一条负向测试，注入什么？
   *参考思路*：找你们最近一次"人肉发现"的生产缺陷（作者实例：CRLF），把它的
   复现步骤钉成注入用例——负向测试的优先级=历史疼痛排序，不是覆盖率排序。
