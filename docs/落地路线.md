# 落地路线：怎么把这套东西真正用进产线

> 前提约定：工具只是把「工程化负担」搬走，**工艺判断力、安全责任、验收签字仍然在人手里**。
> 下面的每一步都写了验收标准——不达标就别进下一阶段。

---

## 阶段 0 · 校准（1~2 天）

**目标**：让工具认识你们自己的东西。此阶段不产生任何业务价值，只为后面三步铺路。

| 做什么 | 怎么用 | 产出 |
|---|---|---|
| **先体检，再动手** | `mcopilot forensics probe logs\你的日志.log` | 体检报告：行格式匹配率、逐类事件状态、哪些检测器会因格式跑不了、哪些只是没埋点 |
| 对齐日志格式 | 按体检报告里给的 `line_regex` 起点改 `knowledge/log_format.json` 的 `line_regex` 与 `timestamp_format` | 你们的日志能 100% 解析，不丢行 |
| 对齐事件语义 | 按体检报告里指出的字段名对应关系（如 `target→pos`）改 `knowledge/log_rules.json` 的 `events` 正则 | 关键事件（指令/到位/参数写入/配方）被正确识别 |
| 校准阈值 | 先跑 `mcopilot forensics thresholds 你的日志.log` —— 看每条阈值**离结论翻转点有多远** | 标定优先级表：哪些阈值脆（优先标）、哪些偏严（当前值永远不命中 → 检测器是哑的，不是「没问题」）、哪些配置根本没生效（死阈值/硬编码兜底） |
| 校准阈值（续） | 再用历史真实故障日志跑 `forensics analyze`，看检出结果 | 阈值调到「不漏报真故障、不误报正常波动」 |
| 对齐工艺数据 | 把 MES/生产数据库导成 CSV，列名对应 `spc` 的指标列 | `spc report` 能出图 |
| 对齐伺服波形 | 采一段**单次阶跃**的伺服波形（指令先不动、再跳一次）存成 CSV | `servo diagnose` 能出等效参数与候选根因 |

**验收标准**：
- 拿一段**已知原因**的历史故障日志跑取证，工具能把那条根因排进候选前三 → 说明映射对了。
- 拿一段**正常**生产日志跑，工具零误报 → 说明阈值不过松。
- `forensics probe` 报告里「因格式跑不了的检测器」降到 0 → 说明适配完成。

> 这一步千万别省。日志映射不对，后面所有分析都是错的，而且错得很自信。
> `probe` 就是为了让这一步从「凭感觉改正则」变成「照着报告逐条改」。

## 阶段 1 · 止血（1~2 周）

**目标**：解决当下正在流血的问题。这一阶段的收益最直接、最容易说服人。

### 1.1 偶发定位偏差/时序竞争/丢包
```bat
mcopilot forensics analyze logs\2026-10-18.log --out out
```
- 把**每个**高危结论回到现场复核（工具给了行号，直接看原日志）。
- 根因确认后，转成两条动作：
  - **代码侧**：把复发预防项写成 `knowledge/review_rules.json` 里的一条规则 → 下次提交自动拦住。
  - **埋点侧**：缺的日志字段补上（比如停止原因、参数写入来源模块）→ 下一轮分析能看得更清。

### 1.2 运动参数不再靠试
- 把常用机型的运动参数（距离/速度/加速度/jerk）过一遍 `motion plan`，
  看理论到位时间与现场实测差多少 → 差得多说明参数配置或到位判定有问题。
- 用 `motion gear` 把所有轴的脉冲当量核一遍 → **这一步经常直接查出定位偏差的真凶**。
- 生成的黄金测试向量接进上位机单测。
- **有电子凸轮的机型，把凸轮表也过一遍 `cam check`**：
  段间速度阶跃是手画凸轮表最常见的致命伤（机台「咔哒」声 + 伺服跟随误差报警，表本身看不出问题），
  工具直接给出阶跃速度和「过渡段最少得多宽」；
  没有凸轮表就用 `cam plan` 按梯形剖面生成一份（段接缝处从轴速度归零，天然没有阶跃）。
- **`cam caps` 先确认你们那家卡到底支持什么**：雷赛能整表从上位机下发、
  正运动只能引用控制器侧的表区间、**固高没有凸轮表**（走跟随段+事件交叉）。
  这一项决定了凸轮相关的需求能不能靠「换卡不改代码」落地 —— **三家的语义不能平移**。

### 1.3 报表口径统一
```bat
mcopilot spc report process.csv --metric place_x_mm --group-by lot
```
产线/研发/工艺三方用同一份工具出的数，先把口径谈平，再谈改善。

### 1.4 伺服问题从「老师傅看波形」变成「工具先给候选根因」
```bat
mcopilot servo diagnose logs\step_2026-10-18.csv --accel 1000
```
- 让上位机在**单次阶跃**和**匀速段**各采一段波形落盘（带时间/指令/反馈/速度列）——
  没有这两段波形，伺服问题只能靠现场手感。
- 工具给出：超调、整定时间、振铃频率、等效二阶参数、type-1 判据、候选根因与验证方法。
- **注意分工**：工具负责「该怀疑什么、去测什么」；改哪个增益、要不要做陷波，仍是人上机决定（Q-06a）。

### 1.5 电子凸轮（cam）：单独一张落地表

凸轮是三家里**实现方式最不一样**的一项，别的能力可以一把梭，它不行：
**雷赛能整表从上位机下发**（`dmc_cam_table_unit`，官方 C# 绑定 `knowledge/sdks/official_api/leisai.csv` L957，
`LTDMC.dll` 的 64 位与 32 位 PE 导出表**都已导出**，`dll_exports.csv` L1495 / L6478）、
**正运动表在控制器侧、上位机只能引用区间**（`ZAux_Direct_Cam` 只传起止点/倍率/距离，`zmotion.csv` L45）、
**固高根本没有凸轮表**（`gts.csv` / `gts_hdr.csv` / `gts.dll` 导出表里 "cam" 符号各 0 个）。
所以下表把凸轮单独拉出来，按阶段写清交付物、前置、验收标准与退路。

| 阶段 | 交付物 | 依赖的前置 | 验收标准 | 失败时的退路 |
|---|---|---|---|---|
| **阶段 0 · 校准**（桌面，不接运动） | ① 一张 `cam plan` 生成的基准凸轮表（CSV + JSON）② 一份 `cam check` 自检报告 ③ 三家能力差异结论（`cam caps`） | 现场提供：从轴行程 / 速度上限 / 加速度上限、主轴行程与转速、你们现有的凸轮表（若有） | **判据是通的**：样例表（故意留了阶跃）必须被判「不通过」（第 7 段接缝 Δv = 72.000 mm/s = 从轴速度上限的 24%），生成的基准表必须判「通过」 | 判据不生效 → 先查 `--slave-v-max` 给了没、严重度是不是按「÷ 从轴速度上限」算的；**这一步不过就不许进阶段 1**（表算不对，现场一定调不对）|
| **阶段 1 · 止血**（离线把在用的表过一遍） | 每张在用凸轮表的 `cam check` 报告：段接缝阶跃、从轴峰值速度 / 加速度、跟随误差预算 | 主轴**实际**转速曲线（不是额定值）；从轴位置容差与伺服等效带宽（给了 `--freq` / `--tol` 才出 CAM-06）| 在用凸轮表**零高危**（CAM-04 高危 = 阶跃占比 > 20%，`velocity_step_limit_ratio`）；中危条目逐条有处置结论 | 有高危但表改不动 → 降主轴转速把阶跃压到 ≤ 5%（`velocity_step_warn_ratio`）；或用 `cam plan` 重生成一张段接缝处速度归零的表 |
| **阶段 2 · 固化**（适配层按厂商语义落地） | ① 凸轮**能力声明**（有无凸轮表 / 表能否从上位机下发 / 语义是查表还是事件驱动）② 雷赛：通用两列表 → `dmc_cam_table_unit` 的转换器 ③ 正运动：控制器侧建表脚本 + 上位机只引用区间 ④ 固高：不落凸轮表，改走跟随段 + 事件交叉 | 厂商给出凸轮表**最大点数 / 表号数量 / `SrcMode` 语义**（否则转换器写不出来）| 契约测试断言「能力声明 == 实际行为」：雷赛回读点数与下发一致、正运动区间引用能跑、固高**不做凸轮断言**（因为没有）| 厂商手册不到位 → 只落**能力声明**，凸轮表下发**显式抛异常**（与本仓其它待确认项同口径），不猜上限、不猜枚举 |
| **阶段 2 · 固化**（上机联调） | 现场记录：接缝处跟随误差峰值、转矩峰值、异响、过渡段实际主轴宽度 | 阶段 2 的表已能下发；伺服波形能采到 | **三个现象落在同一段接缝**上才算数（跟随误差尖峰 / 转矩尖峰 / 异响）；接缝阶跃占比 ≤ 5%；详细判据见 `docs/首次上机验证清单.md` 的 L0 与 L7 | 对不上 → 先怀疑主轴在凸轮生效区间内加减速（CAM-08）与单位口径，**不要先改凸轮表**；改表前先把现场波形留档 |

> 阶段 2 的现场判据、限速口径与「三者对得上才算数」的确认方法，
> 见 `docs/首次上机验证清单.md` 的 **L0（桌面自检）** 与 **L7（电子凸轮）**。

**验收标准**：
- 至少 1 个真实故障被工具定位到根因（且不是靠人工先知道答案再看报告凑出来的）。
- 至少 1 条 review 规则是**因为这次故障才加的**，且之后确实拦下过一次。

## 阶段 2 · 固化（3~6 周）

**目标**：从「有人用」变成「不靠人也跑」。

### 2.1 适配层归一（对应 R-03 / Q-04）
1. 把 `out/csharp/IMotionController.cs` 放进你们的工程，作为唯一运动入口。
2. 业务代码逐步改成只依赖 `IMotionController`，不再直接调 `dmc_*` / `ZAux_Direct_*`。
3. 每个品牌写一个继承 `MotionContractTests` 的类，**接新卡必须跑通契约测试**。
4. 补齐 `knowledge/sdks/*.json` 里 `needs-manual-check` 的项——这是**你们厂商手册的信息，人工填一次，永久复用**。
   **手上有官方 SDK 头文件/官方 C# 绑定时，优先用它而不是手册**：绑定能直接告诉你函数存不存在、参数几个、类型是什么
   （`knowledge/sdks/official_api/*.csv` 就是这么来的，回归测试会拿它逐条校验每条 P/Invoke）。
5. **插卡之前先跑 `MotionSelfCheck.cs`**：它免 xUnit、编译即能跑，验证仿真器与契约断言口径一致
   （尤其「跟随误差必须非零」「开环轴必须报告无真实反馈」「点动方向与速度符号一致」这三条 ——
   前两条抓反馈口径（假反馈 / 开环轴不误报），第三条抓方向写反）。
   仿真器都自相矛盾，接真机只会更乱。
6. **按 `docs/首次上机验证清单.md` 分级上机**：L0 桌面自检（**凸轮判据先在离线跑通**，不接运动）→
   L1 读值（含**反馈真伪判定**：ATYPE / 编码器接线）→
   L2 低速点动（方向）→ L3 单轴定位（单位）→ L4 停止语义 → L5 回零（方向必须显式配置）→ L6 插补/飞拍 →
   L7 电子凸轮（**最后做**：接缝速度阶跃现场确认 + 过渡段宽度验证）。
   **上一级不过，绝不进入下一级**。
7. **把 `docs/厂商手册索取清单.md` 发出去**。PDO 映射、IO 位号、错误码表这类东西**只能由厂商给**，
   而且要走工单/FAE 排期，**周期以周计**。晚发一周，适配层就晚一周能上机。

> 做到这一步，「换卡不改业务代码」才第一次是真的。

### 2.2 评审进 CI
```bat
mcopilot review ..\Source --out out
```
- 高危命中 → 提交不通过。
- 规则包由团队共同维护：每次线上问题复盘，沉淀一条新规则。

### 2.3 日志与数据流水线
- 上位机补结构化埋点（建议 JSONL，带 `device/axis/lot/ts/事件/参数`），
  让取证工具不用猜正则也能拿到语义。
- 生产数据自动落库 → 每天自动跑 SPC，异常自动推送给工艺。

### 2.4 接 MCP
把工具挂进 IDE，工程师不用切窗口、不用记命令。

**验收标准**：
- 换一张卡，**业务代码零改动**（只换适配器实现）。
- 契约测试在 CI 里跑，高危规则命中会让流水线变红。
- SPC 异常能自动推送，不需要人记得去跑。

## 阶段 3 · 进阶（二期，按 ROI 排序）

这些**还没做**，但按需求基线的价值密度排序，做了收益很大：

| 候选 | 对应需求 | 为什么值得做 | 难度 |
|---|---|---|---|
| **视觉标定工具**（手眼/九点标定 + 残差分析 + 漂移监控） | Q-08、R-05 | 标定残差是亚像素精度的地基；漂移趋势比单次残差更能预警 | 中 |
| **配方寻优**（历史数据 → 参数推荐） | R-05~R-07 | 工艺知识本来就在代码和配方里，挖出来是复利 | 中高 |
| **寻光算法离线仿真**（功率计数据回放） | R-07 | 上机调寻光很贵，能离线对比策略就能省大量机时 | 高 |
| **点胶路径离线生成** | R-06 | 只算路径不点胶，节拍与胶量可先算清 | 中 |
| **MES/SECS-GEM 对接一致性校验** | R-08、Q-09 | 协议版本对齐是最耗人的活，值得自动化 | 高 |
| **技术方案/接口文档从代码反向生成** | R-10 | 文档滞后是上位机团队的老毛病，代码反向生成能根治 | 低 |

> 选哪个，先看你们**当下最痛**的是哪个。二期不要一次全上。
>
> 「伺服波形分析」已从本表移出——它在阶段 1 就该做了（见 1.4）。
> 顺带说明需求基线的口径变化：Q-06 拆成了 Q-06a（在线自整定，留人）与 Q-06b（离线诊断，AI 可承担）。

### 为什么二期现在不做（判断依据，不是拖延）

1. **阶段 0 没做完，喂不饱二期。** 二期的六个候选几乎全部依赖**同一条数据流水线**——
   产线日志、工艺 CSV、伺服波形。阈值还是通用起点、日志正则还没对上你们现场的时候先做二期，
   等于把同一个口径问题复制到六个工具里，越做越返工。
2. **输入不在手上，写了也无法验证。** 视觉标定要标定板与相机参数、配方寻优要历史批次数据、
   MES 一致性校验要对方的协议版本、点胶路径要胶路与阀体参数——**这些都不是能从仓库里推出来的东西**。
   缺了输入硬做，产出的只是「能跑但没人能验证」的空壳，比不做更危险。
3. **ROI 排序的前提是先有 ROI。** 上表按需求价值密度排，但「当下最痛哪个」是**现场信息**，
   要等阶段 1 的取证、运动参数、报表口径三件事跑完才知道。**先跑一期的收益是确定的，二期不是。**
4. **一期还有没挖完的存量。** 正运动 `zauxdll2.h`（216KB）与 `zmotion.h`（66KB）还没逐条纳入 `zmotion.json` 的 P/Invoke
   （**真值 CSV 已经导出**：官方 C 头文件比官方 C# 绑定多声明 **25 个**函数 ——
   **24 个在 `zauxdll.dll` 的 PE 导出表里找得到，1 个（`ZAux_GetTraceFile`）导不出**，
   绑上去等于上机必炸 `EntryPointNotFoundException`，所以本项目**不绑**它；
   另有 **144 个 `ZMC_*` 独有函数**在 `zmotion.dll` 里，144/144 全部导得出，可全量纳入）——
   **这一件的边际收益高于二期任何一项**（它直接决定适配层能不能上真机）。
   固高这一件**已经做完了**：官方 `gts.h` / `gts.cs` / 5 个 `gts.dll` 都已到手，
   34 条绑定逐条对齐官方 C# 绑定与 C 头文件、对齐 DLL 导出表，`needs-manual-check` 已全部清零；
   剩下的是**厂商侧的三件事**（当量公式、现场实际型号与固件、GEN 的 SDK 包），不是我们能自己做完的事。

## 落地前提（说清楚免得白干）

1. **必须有人愿意把日志贴进来。** 工具再好，日志里没有的信息它也变不出来。
   上位机的埋点质量直接决定取证上限。
2. **阈值要按你们的产线校准。** 通用阈值只是起点。
3. **规则包会过时。** 业务改了、设备换了，规则要跟着改——这是持续成本，不是一次性投入。
4. **不要指望它替代老师傅。** 它的价值是把老师傅的判断**沉淀成可复用的检查项**，
   而不是取代他。R-11（带助理工程师）这条 AI 只能沾一点边。
5. **安全相关的绝不自动化。** 急停、联锁、力控保护参数，工具连建议都不该给。
