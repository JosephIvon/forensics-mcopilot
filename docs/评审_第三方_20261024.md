## 一、总评

**这是一份"厂商知识层钉得很死、算法层与门禁层明显松"的工程。**

- 强项是真的：官方 C# 绑定 → PE 导出表 → C 头文件三层真值交叉、四层返回类型真值、真实语料夹具逐行断言、负向门禁的三重注入纪律、故障农场与接入闭环——这套东西的骨架是对的，很多细节能看出是踩过坑才写出来的（`test_每条PInvoke必须被对应DLL真正导出` 用导出表兜住"官方声明 ≠ DLL 导出"这一类真机即崩，是本仓最值钱的一条断言）。
- 问题也集中且具体：**门禁的"绿"比它自己以为的弱**。1 道 CI step 吞掉 5 道门禁的失败信号；2 道门禁在干净检出上结构性不执行；1 道门禁在缺仓环境下结构性失明；真值层自己少了一条声明而无人察觉。

**一条判断先给出：** CI 全绿 ≠ 结论成立。本仓最核心的"每条结论钉在真值上"这个主张，在**门禁层**被自己削弱了——不是结论错了，是**证明结论的那道门没有牙齿**。

## 二、发现清单

### P0-1 ｜ CI 里 6 道文档门禁只有一个的退出码算数

**位置**：`.github/workflows/gates.yml:50-59`（步骤「文档与电子书同步门禁」）

```yaml
run: |
  python scripts/verify_bilingual_parity.py
  python scripts/verify_doc_refs.py
  python book/tools/check_doc_refs_heads.py
  python book/tools/verify_crops_verbatim.py
  python book/tools/check_vol2s_structure.py
  python book/tools/verify_book_numbers.py
```

**触发条件**：该 step 是 6 条 native command 串在一个 pwsh 块里。GitHub Actions 的默认 pwsh shell 只把**最后一条**命令的 `$LASTEXITCODE` 带出 step；`$ErrorActionPreference='Stop'` 管不了 native command（`$PSNativeCommandUseErrorActionPreference` 默认 `$false`）。因此**除最后一条外的任意一条失败，step 仍然绿**。

**影响**：README 中英不同步、文档行号引用失效、裁剪件被改、书结构违规、书里的数字对不上——这 5 类破坏任意一类发生，CI 全绿。其中 `verify_doc_refs.py` 正是本仓"每条结论钉在真值上"的主检查。

**是否实测**：**是**（本人在干净副本 `<评审机>\clones\fmcp_p0c` 实跑）

```
基线（6 条原样跑）                      → STEP_EXIT=0
第 1 条强制 exit 3，其余不变              → STEP_EXIT=0     ← 失败被吞
单独跑被改坏的第 1 条                     → CMD_EXIT=3      ← 它自己确实红
```

**最小修复**：拆成 6 个独立 step，或每条后加 `if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }`。
**修复代价**：约 10 行。**优先级**：最高——它一条就吞掉 5 道门禁的失败信号。

### P1-1 ｜ 真值层少了一条正运动声明，厂商 EntryPoint 笔误被去重逻辑吞掉

**位置**：`scripts/extract_binding_returns.py:85-86`（以 EntryPoint 作为主键）、`:125-128`（同主键去重、只累加 `重复次数`）

**触发条件**：厂商官方 C# 绑定 `正运动_ZMotion/SDK_头文件/Zmcaux.cs:4518-4519` 有一条复制粘贴笔误：

```csharp
[DllImport("zauxdll.dll", EntryPoint = "ZAux_Direct_SetVectorBuffered2", ...)]   // ← 写错了
public static extern Int32 ZAux_Direct_GetVectorBuffered2(IntPtr handle, int iaxis, ref float pfValue);
```

方法名是 `Get…2`，EntryPoint 却仍指向 `Set…2`。抽取器以 EntryPoint 为主键，于是这条 Get 方法与上一条 Set 方法撞键，被 `continue` 掉，**表里没有它**。

**证据（本人在厂商原件与仓内真值表上实算）**：

| 项 | 实测 |
|---|---|
| `knowledge/sdks/official_api/zmotion.csv` | 402 条声明 / 402 个唯一函数名（README:133「正运动 402 个函数」✓） |
| `binding_returns.csv` 中正运动行 | **401**（`zauxdll.dll` 398 + `zmotion.dll` 3） |
| 缺失的那一条 | `ZAux_Direct_GetVectorBuffered2`（`zmotion.csv` 有，`binding_returns.csv` 无） |
| 全表 `重复次数 > 1` 的行 | **恰好 1 行**：`zauxdll.dll!ZAux_Direct_SetVectorBuffered2`，重复次数 = 2 |
| 全表 `EntryPoint ≠ C#方法名` 的行 | **0 行**（因为撞键的那条已被丢弃，表里根本显示不出错配） |
| 按来源文件求和 | 806(雷赛) + 474 + 475 + 474 + 475(固高 4 变体) + **401**(正运动) = **3105**（= 表内实际行数 ✓） |

**影响（两层）**：

1. **表不完整且无信号**：`zmotion.csv` 的 402 条声明里，有 1 条在返回类型真值层没有落点。第四层被 README 描述为"厂商官方 C# 绑定自己的返回类型（3105 条）"，读者会当作全覆盖。没有任何测试断言这条覆盖关系——`tests/test_binding_truth.py:77` 只有 `len(binding_rows) > 3000` 的下限，放行 3105 或 3104 一样绿。
2. **厂商笔误被本仓的"笔误探测器"漏掉**：本仓的立身之本是"照抄官方绑定会踩坑"（`.self-improving/lessons.md:13`、`:29`，已点名 `ZAux_Direct_GetNtype` 与 `GT_GantryHoming`）。这条 `EntryPoint` 错配属于同一类危害，但**危害形态不同**：`dll_exports.csv` 显示 `zauxdll.dll` 64 位**同时导出** `ZAux_Direct_GetVectorBuffered2` 与 `ZAux_Direct_SetVectorBuffered2`，所以照抄这段绑定去调用 `ZAux_Direct_GetVectorBuffered2` **不会抛 `EntryPointNotFoundException`**（不会崩），而是实际调用了 Set 导出 → **静默写错值**。这是比"崩"更难查的一类。本仓现有三层校验（声明 / 头文件 / 导出表）全部以"函数名"为键，**天然看不见 EntryPoint 写错**；唯一能看见的位置（抽取器）恰好把它去重掉了。

**是否实测**：**是**（逐条比对了厂商原件 `Zmcaux.cs:4508-4519`、仓内 `zmotion.csv` / `binding_returns.csv` / `dll_exports.csv`，并按来源文件复算总数 3106 vs 3105）

**最小修复**：
- 抽取器改为**以 C# 方法名为主键**，EntryPoint 单列一栏；两者不等时**保留该行并标记**，不要 `continue`。
- 补一条断言：任一来源文件抽取出的方法数必须等于该文件 `[DllImport] + extern` 配对数（当前 402 vs 401 会立刻红）。
- 把这条厂商笔误**写进 `knowledge/`**（现有 `leisai_io_bits.csv` 之类"厂商件 + 结论"的表正是干这个的），并在 `docs/` 留档：厂商 `Zmcaux.cs` 的 `ZAux_Direct_GetVectorBuffered2` 不可照抄。

| **注释漂移** | `spc.py:106` 注释写"判异规则：连续 7 点同侧 / 连续 7 点递增或递减"，实现是 **9 点同侧**（`:134-135`）与 **6 点递增/递减**（`:136-142`）。报告里输出的规则名是对的（"连续 9 点在中心线同侧"），**只有注释错**——但按注释调机会出错的现场工程师会按 7 点排查 |
| σ 双轨 | `:101` `sigma = mr_bar / 1.128 if mr_bar > 0 else stdev(values)` —— 兜底分支用的是 **样本标准差 (n-1)**，与正路线的 `MR̄/1.128` 不是一套口径，两条分支都没测 |

**最小修复**：用解析可算序列（如 `[1..10]`）断言 `cl == 5.5`、`sigma == mr_bar/1.128`、`ucl == cl + 3*sigma`、`mr_ucl == 3.267*mr_bar` 的绝对值；顺手把 `:106` 注释改成 9/6。

## 四、没查的 / 风险

**没查的（明确不覆盖）**：

1. **真实硬件路径**：串口（com0com / RTU 超时契约）、PLC 联机、EtherCAT 主站、真实伺服与相机。G3/G4 的契约测试在 CI 上是**桩对桩**，不接设备。
2. **Roslyn / `csc` 真实编译面**：`csc` 由 `gate_protocol.ps1` 在 Windows runner 上调，本人在本机未复刻完整 G1–G12 门禁执行（只跑了文档侧与 pypdf/阈值侧）。
3. **Windows 现场上机**：没有真实控制器、没有真实相机、没跑过 `docs/首次上机验证清单.md` 里的任何一项。
4. **电子书正文的事实性**：只核了结构、裁剪件一致性与行号引用坐标，**没有逐句核对书里的技术断言**是否与厂商手册相符。
5. **`scripts/` 与 `book/tools/` 下约 110 个脚本的判定逻辑本身**：除本报告点名的以外，只验证了"能跑完不崩在打印上"。

**风险（读者必须知道）**：

- **CI 全绿 ≠ 结论成立**。P0-1 一条就吞掉 5 道门禁；P1-3 让文档断链在 CI 上 100% 不可见；P1-5 让"引文是不是编的"在 CI 上从不执行。这三条合起来意味着：**CI 的绿灯目前不能被读作"文档与真值一致"**。
- **门禁红 ≠ 结论错**。P1-4 的崩溃是诊断丢失，不是判定错误；P2-2 的死阈值是已知未闭环项。
- **CI 与本机环境不同**：本机 `%WORKSPACE%/mcopilot-external` 在位，CI 不在。P1-4、P1-5 的结论都是**面向 CI / 公开 clone 场景**的；本机跑同一批门禁得到的是另一条分支。
- **锚点门禁在 CI 上核验了 0 个锚点**：`anchors.json` 登记的 16 个锚点路径全部指向仓外或 `out/`（逐条比对 `git ls-files`：16/16 未跟踪）→ 干净检出上 16 个全部 SKIP → exit 0。SKIP 本身有喊明（"不得把本次结果读作『全部已核』"），这点做得对；但读者若只看 CI 绿灯，会以为外部真值被核过了。**更要紧的是**：指纹只存在于仓内可改的 `anchors.json`，改掉原件 + 同 commit 改掉 manifest 里的 sha256，所有门禁仍全绿。
- **P1-1 揭示的更深一层**：本仓的三层校验（声明 / 头文件 / 导出表）全部以**函数名**为键，**结构上无法发现 EntryPoint 写错**。这类问题目前没有防线。
