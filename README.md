## 一、这套东西为什么存在

**工业现场真正拖住工程师的，从来不是「代码写不出来」，而是这四件事：**

1. **证据散落** —— 一次偶发定位偏差，要翻日志、翻波形、翻参数写入史，结论无法追溯；
2. **口径不统一** —— 产线、研发、工艺各算各的良率，数字对不上就没法讨论；
3. **换卡要重写** —— 「换卡不改业务代码」停留在口号，没有回归测试盯着它；
4. **规格靠记忆** —— 厂商函数的参数个数、返回宽度、IO 端子位号，抄错不报错，上机才炸。

把**工业需求基线**（20 条：11 条工程职责域 + 9 条工程能力要求）逐条量化后，结论很明确：

**AI 能吃掉的是「工程化负担」，不是「工艺判断力」。**

AI 承担度最高的几块有个共同点：
**① 产出物是文件而不是手感 ② 能被规则或数值验证 ③ 错了能被机器发现**。

| 优先级 | 需求条目 | AI 承担度 | 对应工具 |
|---|---|---|---|
| ★★★ | R-03 运动卡适配层与品牌能力矩阵 | 85% | `adapter` |
| ★★★ | R-09 现场疑难问题攻关（偶发偏差/丢包/良率波动） | 80% | `forensics` |
| ★★★ | R-10 软件工程规范与文档 | 85% | `review` |
| ★★☆ | R-08 SPC 统计、稼动率与报表 | 75% | `spc` |
| ★★☆ | **Q-06b 伺服波形的离线诊断**（实测波形 → 参数 → 根因） | **75%** | `servo` |
| ★★☆ | R-04 / Q-05 多轴联动与插补的算法层 | 45~50% | `motion` |
| ★☆☆ | R-05~R-07 工艺（贴片/点胶/耦合）参数挖掘 | 35~50% | `spc` + 二期 |
| — | **Q-06a 伺服在线自整定/惯量辨识**、力控手感、产线验收签字 | ~0~15% | **明确不自动化** |

**Q-06 被拆成了两条**，因为它们经常被混成一句「伺服整定难自动化」，那样会漏掉一整块：

- **Q-06a 在线自整定 / 惯量辨识 / 共振规避（现场闭环操作）** —— 需要示波器 + 上机，AI 不介入闭环，**留人**。
- **Q-06b 离线波形诊断（读波形 → 反推等效参数 → 候选根因与验证方法）** —— 纯离线、可数值验证，**AI 可承担**。

**明确交给人、不碰的四件事**：伺服在线自整定与惯量辨识、安全联锁与急停参数、工艺窗口定版、产线验收签字。
原则一句话：**AI 出草稿和检查项，人做决定和签字；凡是「错了会伤到设备或人」的，一律不自动化。**

完整拆解见 `out/requirements_map.md`（运行 `mcopilot requirements report` 生成），
机器可读版在 `knowledge/requirements_map.json`。

### 需求基线是什么、从哪来

`knowledge/requirements_map.json` 是这套工具的**唯一需求事实源**，条目口径是**工程交付物**，不是岗位描述：

- **11 条工程职责域（R-01 ~ R-11）**：上位机全流程交付、架构分层与设备抽象层、运动卡适配层、
  多轴联动与工艺运动、共晶贴片 / 点胶 / 耦合工艺、设备接口与数据采集、现场疑难攻关、
  软件工程规范与技术带教；
- **9 条工程能力要求（Q-03 ~ Q-10，其中 Q-06 拆 a/b）**：C#/C++ 工程能力、多品牌运动卡 SDK、
  多轴联动与电子凸轮、伺服在线整定与离线诊断、视觉标定、数据与通信能力、跨部门技术输出。

**编制口径**：按运动控制上位机软件工程的**实际交付物清单**编制；编制过程中拿行业在招岗位语料做过
一次**交叉核对**（`docs/requirements_provenance_20261021/`），只用它确认基线**没有遗漏工业界普遍要求的
能力项**，不用它决定基线的口径。
**学历、工作年限这类招聘资历筛选条件不构成工程交付要求，已明确排除**（见 `meta.excluded_from_baseline`）。

## 三、八个智能体（九个模块）

### 1. `adapter` —— 运动卡适配层与能力矩阵
> 对应需求：R-03、Q-04、Q-03、R-02

厂商函数手册 → C# 适配器 + P/Invoke 声明 + 跨品牌契约测试 + 品牌能力矩阵。

```bat
mcopilot adapter gen --sdk dmc --out out
mcopilot adapter matrix --out out
```

> `--out out` 指的是**产物根目录**；C# 源码会统一落在 `out\csharp\` 下（不要写成 `--out out\csharp`，会多套一层目录）。

**解决的真问题**：
- 统一抽象层把「业务层只准用 mm/mm·s⁻¹」变成硬约束，脉冲换算只允许出现在适配层内部 → 换卡不改业务代码。
- 能力矩阵把**位置/速度单位口径**摆在一起。已收录的关键差异：雷赛用 `pulse/s`、正运动用 `单位/秒`（由 `UNITS` 决定）、
  **固高用 `pulse/ms`（比 `pulse/s` 小 1000 倍）**——**照抄速度参数节拍可能差 1000 倍，而且机器不报错**。
- 契约测试让「换卡不改业务代码」这句话能在 CI 里变红变绿，而不是靠人自觉。
- **反馈真伪由适配层如实声明**（`HasRealFeedback(axis)`）：正运动 ATYPE=1/7 脉冲轴上 MPOS 只是 DPOS 的副本，
  跟随误差**必然**恒为 0 —— 契约测试据此判为不适用，不在开环轴上误报「反馈是假数据」，
  也不会逼着人去改本来正确的代码。

**工具不猜厂商行为**：查不到的函数在生成代码里标 `TODO[需核对厂商手册]`，在矩阵里列成待办清单。
支持显式失败（抛 `NotSupportedException`）好过提供一个错误实现 ——
**总线轴的伺服使能就是显式失败的**：CiA402 序列与 SDO 入口都已核实，
但「使能由控制器内部完成还是主机写 PDO」没定死之前，我们不替厂商做这个决定（写控制字属于可能让电机突然动作的机器安全动作）。

**每条 P/Invoke 都对着厂商官方 SDK 绑定逐行校验**（`knowledge/sdks/official_api/*.csv`，
由官方 C# 绑定导出：正运动 402 个函数、雷赛 **1466 条声明 / 1463 个函数名**）。回归测试会检查
**函数名存在、DLL 名一致、参数个数一致** —— 这不是风格检查：
拿到官方绑定之前，本仓库里**正运动的 `ZAux_Direct_SetAxisParam` 和雷赛的 `dmc_set_home_profile`
在官方 API 里根本不存在**，真机上分别是「建连即崩」和「回零即崩」。
声明一个不存在的函数比缺实现更危险：它不报错，只在真机上炸。

**第三家：固高 GTS（官方绑定级，三层真值齐了）**。2026-10-20 拿到固高官网 SDK 包后，
固高从「只有手册 PDF 的降级绑定」升级为**与雷赛/正运动同一档**：
官方 C# 绑定 `gts.cs`（473 条 DllImport / 30 个结构体）、
官方 C 头文件 `gts.h`（535 条 `GT_API` 声明、200 个宏）、
4 个 `gts.dll` + MCT2008 自带那份的 **PE 导出表**，全部导出成
`knowledge/sdks/official_api/gts.csv` / `gts_hdr.csv` / `gts_structs.csv` /
`gts_hdr_macros.csv` / `gts_io_terminals.csv`（121 行端子表），并入 `dll_exports.csv`。
34 条绑定逐条对过：**函数名、参数个数、参数类型、ref/out 修饰、字段顺序与字节偏移**全部一致，
且 5 个 DLL 的导出表里这 34 个函数全导得出（`verified` 从 `needs-manual-check` 升为 `official-binding`）。
调用约定不再是推测：官方 `gts.h` 第 3 行 `#define GT_API extern "C" short __stdcall` → `StdCall`。
这一轮真值直接抓出三个真问题：

- **`GtsHomePrm` 少 8 字节 = 内存越界写**：官方 C# 绑定的 `THomePrm` 是 23 个字段（88 字节），
  官方 C 头文件的 C 写法是 `long pad3[2]`（80 字节）—— **厂商自己的两个件差 8 字节**。
  适配器回零要先 `GT_GetHomePrm` 读回再改字段，**DLL 会把 88 字节写进我们的结构体**，
  按 80 字节实现就是越界写。已按 88 字节（官方 C# 绑定）实现。
- **保留位编号基准搞反了**：手册用 0 基（`pad1[0]`、`pad2[1]`），官方 C# 绑定用 1 基（`pad1_1`、`pad2_2`）。
  手册的「启动时检测限位/原点」标志是 `pad2[1]`（**第二格**），原先放第一格 → 启用检测不生效。
- **官方 `gts.cs` 里 `GT_GantryHoming` 随包 DLL 根本没导出** → 照抄官方绑定就会 `EntryPointNotFound`
  （同类：正运动 `ZAux_Direct_GetNtype`）。**所以第三层「DLL 导出表」不能省。**

另外顺带查实：**GEN（`GTN_`）不在这个 SDK 包里** —— `gts.h`/`gts.cs`/5 个 DLL 里 `GTN_` 符号一个都没有，
GEN 是独立产品线（自带用户手册与基本功能手册），它例程里的 `#include "gts.h"` 只是同名文件。
要接 GEN 必须单独要 GEN 的 SDK 包。
固高**没有** `SetPulsePerMm`/`GetPulsePerMm` —— 当量是 `GT_ProfileScale` 的分数比且手册没给公式与方向，
所以适配器**不下发**当量变换，要求控制器保持默认 1:1。

**雷赛也升到「手册级四层真值」**。把《DMC3000 系列卡用户使用手册 V2.0》（334 页）从 1.4 订货信息
一直读到附录 13，逐条核对后，**推翻了我们自己 3 处与手册冲突的实现**：

- **锁存通道不是靠参数选的**：`dmc_set_latch_mode` 的 `triger_chunnel` 是**保留参数固定 0**，
  **通道由轴号决定**（LTC0 锁 0~3 轴、LTC1 锁 4~7 轴）；触发口是 **IN14/LTC0、IN15/LTC1**（表 8.3），
  **不是原先写的「IN4~IN7」**。`dmc_set_ltc_mode` 的 `ltc_mode`/`filter` **也是保留参数固定 0**
  （原先当成「AB 相/锁存信号」和「去抖时间」传了自造值）。锁存去抖配置项已删（保留参数，配了也不生效 = 死配置）。
- **`IsEnabled` 原先读的是厂商「内部使用（保留）」的函数**：`dmc_get_sevon_enable` 在官方 `LTDMC.cs` 里
  被标在「//内部使用（保留）」下，返回值语义未公开 → 改用手册 8.13 明确写了语义的
  **`dmc_read_sevon_pin`**（返回 SEVON 端子电平 0/1，按**轴号**、专用端子、不占通用输出位），
  并新增 `ServoOnActiveLevel` 配置项（有效电平取决于驱动器接法，不能写死）。
- **脉冲卡根本没有轴状态机函数**：`GetState` 原先调 `nmc_get_axis_state_machine` ——
  那是 **EtherCAT 总线轴专用**的函数，脉冲卡上调用只会失败或给出总线轴语义。
  改按手册 8.7 的 `dmc_axis_io_status` 位图（ALM/EL±/EMG/ORG/SL±/INP/EZ/RDY/DSTP）+ `dmc_check_done` 自行映射。
- 顺带查实：**脉冲上限 4 MHz**（表 1.1，原先写的 5 MHz 是错的）、高速比较 `hcmp` 0~3 **一一对应 CMP0~CMP3**
  （原先记着「随系列而异、不能跨型号套用」）、`dmc_set_ltc_mode` 等的**保留参数一律传 0**。

雷赛这一轮导出的真值：`leisai.csv`（官方 C# 绑定 **1466 条声明 / 1463 个函数名**）/

### 1b. 雷赛总线卡 / 独立控制器（DMC-E / EMC）—— 当量模型与脉冲卡**完全相反**
读完《雷赛控制 EtherCAT 总线卡用户使用手册 V2.0/2024.11》（350 页）与
《EMC 系列总线型独立式控制器用户使用手册 V2.0/2024.1》（271 页）后，**推翻了两条既有结论**：

- **当量模型反过来了**。脉冲卡（DMC3000）是**软件侧**除脉冲当量；总线卡/独立控制器是**控制器侧**
  `dmc_set_equiv(CardNo, axis, equiv)`（设 100 → 控制器发 100 位置 = 1mm，**速度单位随之变 mm/s**），
  **这时反而不该在软件侧换算**。**两套模型混用 = 位置整体差一个当量倍数** ——
  已写成回归测试，钉住「脉冲卡适配器不得调用 `dmc_set_equiv`」。
- **EMC 不是另一套函数库**：它用**同一个 `LTDMC.dll`、同一套 `dmc_`/`nmc_` 函数名**
  （官方 EMC 包 804 条声明里 `emc_` 前缀 **0 个**，EMC 手册自己的 C 原型也全是 `dmc_`），
  差别只在 `dmc_board_init_eth(IP)` 走以太网、以及「卡号」是链接号。
  知识库里原本同时留着「共用同一套库」和「EMC 是另一套库」两条矛盾结论，本轮已订正并加测试钉住。

另外挖出**两处真笔误**：EMC 手册把 `dmc_emg_stop` 写成 `dmc_EMG_stop`、`dmc_axis_io_status` 写成
`dmc_axis_IO_status`（正文 + C 原型 + 附录 4 索引三处都错）。**PE 导出名大小写敏感，照抄必炸** ——
判据是三方一致：EMC 官方 C# 绑定 + 三个版本 DLL 导出表都只有全小写。
另有 10 处 `position→positIOn` 是 **PDF 文本层字形伪影**，不是笔误，**不误报厂商**。

**还剩两处没敢自己定**（已写进给厂商的清单）：① 附录 3 表 F3.0 里 **15 行的 PDO 方向与 CiA402 惯例相反**，
方向搞反 = 轴不动 / 状态读不到；② **EMC 没有专用 EMG 急停端子**，手册建议用通用输入口做 IO 映射，
现场没做映射**等于没有急停**。这两项确认前，**总线轴适配器不落地**，总线轴 `Enable` 保持显式失败。

### 1c. 第四层真值：**厂商 C# 绑定自己写的返回类型**（含 DLL 变体口径）

前三层真值各管一段，但**返回类型一直比不了**：

| 层 | 语言 | 有返回类型？ | 对一条 C# 声明的适用性 |
|---|---|---|---|
| PE 导出表 | 符号名 | ✗ | 只能证明「函数存在」 |
| `official_api/{gts,leisai,zmotion}.csv` | C# | ✗（原型列只给参数） | 参数可比，返回类型比不了 |
| `official_api/*_cpp.csv`、`gts_hdr.csv` | C | ✓ | 比得了，但**口径错位**：Windows(LLP64) 下 C 的 `long` 是 32 位，C# 的 `long` 是 Int64 |
| **厂商官方 C# 绑定源码** | **C#** | **✓** | **C# 声明该对标的就是这一层** |

第四层补上后，「返回类型对不对」不再需要跨语言换算。做法是**新增可复现的抽取器**
`scripts/extract_binding_returns.py`，直接从厂商原始 C# 绑定源码抽，产出
`knowledge/sdks/official_api/binding_returns.csv`（**3106 条**）：

### 2. `servo` —— 伺服波形离线诊断（**逆向**的那半条链）
> 对应需求：Q-06b（离线诊断）；Q-06a（在线整定）明确不做

`motion` 是**正向**：给定参数算误差。本工具是**逆向**：由**实测波形**反推伺服状态与根因。

```bat
mcopilot servo diagnose wave.csv --accel 1000
mcopilot servo synth --model 2inertia     :: 合成已知真值的波形，用来验证估计器
```

> ⚠ **报告的「证据依据」小节是必读项。**
> 结论算不算数，取决于**波形从哪来**，不取决于工具跑得多认真：
>
> | 波形来源 | 依据类型 | 能说明什么 |
> |---|---|---|
> | `synthetic_fixture`（仓库自带的 3 个夹具） | **自洽性验证** | 真值与波形**同源**（同一组模型参数）→ 诊断与真值相符是**同义反复**，**不构成有效性证据** |
> | `synthetic_model_truth`（`servo synth` 产出） | 自洽性验证 | 同上，能验「估计器能把同一个模型解回去」 |
> | `real_record`（真机记录，如 `samples/servo/twincat_export10.csv`） | **外部证据** | 独立基线见 `twincat_export10.truth.json`（厂商元数据 + **不经本工具**的复算）；结论须与基线对齐才算数 |
> | `unknown`（你自己采的波形） | 未知 | 报告会明说「无法判断依据类型」 |
>
> 标签写在 **CSV 头**（`# provenance: …`）与 `.truth.json` 里，工具据此自动标注；
> 判定测试见 `tests/test_mcopilot.py` 的「证据分级（A-87）」一节。
>
> `mcopilot all` 会**同时**产出两份伺服报告：`out/servo_sample.md`（夹具 · 自洽性验证）
> 与 `out/export10.md`（真机记录 · 外部证据）—— 只给夹具就等于只给「自己造自己评」。

做的事：

- 标注超调量、峰值时间、整定时间、振铃频率（过零法）、尾段不收敛。
- **最小二乘拟合等效二阶参数**（ωn/ζ），并与超调法交叉比对：两者差异大本身就是结论（说明响应不是单一二阶）。
- **type-1 / type-2 判别**：误差与速度的相关系数 **加上** 误差/速度比值的稳定性。
  只有相关系数高是不够的——机械谐振时误差和速度一起振荡，相关系数同样很高，
  但比值忽大忽小；真正的 type-1 是 `err = k·v`（比值恒定），此时 `e≈a/ωn²` 不适用、误差不收敛。
- **恒加速度段的实测跟随误差 vs `e≈a/ωn²`**：先在波形里定位恒加速度段再对比；
  找不到就明说「没做这个对比」，不拿阶跃瞬间的误差冒充。
- 输出候选根因 + 每条根因的「怎么验证」。

**输出遵循 C3 诊断契约**（`schema: mcopilot.servo.diagnosis/1`，源自 axiscope 的 `docs/contracts/C3-diagnosis.md`）。
这不是「多输出一段文字」，是**把结论的成立条件一起交付**：

| 字段 | 作用 |
|---|---|
| `hypotheses[]` | 每条带 `fault_mode`（KB0 §2 的 22 个 slug 之一）、`supporting_evidence`（≥2 条，带判据号与真值来源）、`contradicting_evidence`（**强制存在**，没有就写空数组）、`expected_effect.basis`、`next_data_to_collect`、`counterfactual` |
| `differential.not_evaluable` | 结构性不可评估的规则进这里，**不进 hypotheses**；每行带 `blocked_by` / `why` / `unlocks` |
| `audit` | 每条判据三选一：`rules_fired` / `rules_skipped`（因前提不满足未执行）/ `rules_not_hit`（执行了没命中）—— 三档互斥，不遗漏 |
| `verdict.overall_confidence` | 按 KB4 §2.2：`主结论置信 × (1 − 0.05 × min(4, 去重后的独立缺席原因数))` |

三条硬规矩（都踩过坑才写下来的）：

1. **判据的「状态」必须显式。** 没执行的判据不能算「没发现问题」——报告里分两句说：
   「已执行的判据没有命中」与「另有 N 条判据因前提不满足未执行」。
2. **频率类判据以「谱线绝对幅值 ÷ 误差动态量级」判**，不用带内能量占比、不用相对突出度。
   误差本身很小时，比例会把可忽略的谱线吹成主角（交叉验证 §F-07）。
   同理，落在**最低/最高 bin** 上的「主频」是分辨率边界上的残留，不是频率 —— 报告里会当场说破。
3. **指令刷新率是实测信号**（cmd 跳变间隔中位数的倒数，不是写死的常数）。
   谱线落在刷新率整数倍上时判为**「指令刷新成分，非被控对象响应」**，不进结论、只进 `not_evaluable`。
   它是上位机按固定周期刷新指令造成的，**不是伪谱线**，也不是被控对象的响应。

**知识与代码分离**：阈值、22 个 slug、判据公式全在 `knowledge/servo_rules.json`；
`src/mcopilot/agents/servo.py` 里只有信号计算与通用求值器 —— **改配置不改代码**。

守住这层的测试：

- `tests/test_fault_mode_slugs.py` —— `fault_mode` 集合必须与 axiscope 的 KB0 §2 **精确相等**（不许臆造、不许漏）；
- `tests/test_crossval_regression.py` —— 把交叉验证的失败点锁成回归（F-01 崩溃 / F-03 偏置分解 / F-07 边缘 bin / 刷新率口径）；
- `scripts/verify_servo_spectrum.py` —— 用**纯标准库**独立复算报告里的频域数值
  （**不拿被审的代码验被审的结论**，那是 axiscope 审计里点名的「同源自证」）。

**它的效力边界（必须一起看）**：

1. 估出来的是**等效**二阶参数（≈ 闭环带宽），**不是机械固有频率**。判断共振必须再做扫频确认。
2. `e ≈ a/ωn²` 成立于 **type-2（位置环 + 速度前馈）** 且只描述**恒加速度段**。
3. **时间列单位判定错就是 1000 倍误差**（毫秒当秒 → ωn 差 1000 倍，而报告看上去一切正常）。
   工具按**列名**优先判定（`time_ms` / `t_ms` / `time_us`），并在报告里显示判定结果；
   也可以用 `--time-unit` 显式指定。
4. 本工具**不替代示波器与伺服手册**。它给的是「该怀疑什么、去测什么」，不是「增益该调到多少」。

#### 2.1 v3：转矩/电流通道（cur_q）+ 事件流（events.jsonl）——11 条判据的解锁

```bat
mcopilot servo diagnose wave.csv --events events.jsonl --accel 1000
```

两个新输入（都是**可选**：没有它们，11 条新判据照旧「不可评估」，绝不编）：

- **`cur_q` 转矩/电流列**（列名认 `torque` / `current` / `转矩` / `电流`）——
  解锁机械族的最后四条：起动突破比（静摩擦 SRV-15）、低速粘滑（爬行 SRV-16）、
  转矩窄带纹波（SRV-17）、谐振-误差配对（双惯量 SRV-20）。
- **`--events events.jsonl`**（C6 机器上下文格式：每行一个事件，`t` 为**波形时间轴**秒、
  `source`、`code`，可选 `level`/`axis`/`detail`）——解锁软件族六条：
  host 暂停-误差尖峰因果（SRV-23）、插补欠载（SRV-24）、总线丢周期（SRV-25）、
  视觉迟到（SRV-26）、到位判定过早（SRV-28）、指令轮询滞后（SRV-29）。

**事件分两级，纪律不同**（这是 C2 因果契约的落地）：

1. **事件侧统计**（次数、时长、间隔、p95）——**不需要**同步就能评：
   SRV-24/25/26/29 四条只看事件流本身；
2. **因果级信号**（暂停对齐误差尖峰、done 时误差没收敛）——把事件对到了波形上，
   是因果措辞，**只在事件-波形同步验证通过时**才允许计算：
   `move_started` 与指令跳变沿配对，中位 |Δt| ≤ 时钟预算（默认 5 ms）才算「对齐」；
   配不上时 SRV-23/28 **整条拒答**（`blocked_by=events_sync_unverified`），
   不给「打了折的因果结论」。拒答 ≠ 缺席：此时软件族**不会**触发整族缺席登记。

配套的坑都填了（各有测试锁着）：指令瞬跳会抬高速度基准 → 巡航分段用 p99 不用 max；
阶梯反馈的相邻差分是脉冲串 → 派生速度用跨样本中心差分；全局动态 std 会淹没安静段的
尖峰 → 尖峰基线用**局部环最大值**；到位判定的基线用**其它 done 的自参照中位数**；
误差谱线做物理归因前先过**刷新线门**（47 Hz 的纹波不许配到 100 Hz 的刷新线上）。

**v5 之前不可评的（现已全部有解锁入口，见下）**：SRV-18（驱动器电流环参数）、
SRV-19（扫频）、SRV-21/22（温度通道）、SRV-27（工艺配方上下文）。

**v4：轴铭牌侧车 `--axis axis.json`**（`cpr` / `pole_pairs` / `screw_pitch_mm`）——
给了它，SRV-17 的转矩纹波结论从「存在窄带成分 + 频率」升级成
「**6× 电频率**（逆变器/死区特征）」或「**k× 每转**（机械周期误差）」的阶次归因
（落在 `hypotheses[].attribution`，距最近整数 >0.2 就不归因）。
没有侧车时归因字段缺位——缺位即「未做归因」，不拿猜测冒充。
这份侧车是 C1 样本包文件，**不是 C6 契约对象**（C6 全文没有 cpr 字段）。

**v5：最后一批搁置判据全部解锁**——
- **温度**：CSV 加 `temp` 列 → SRV-21 热漂移（误差慢趋势与温度相关 ≥0.6 且
  每 K 漂移 ≥2 µm）、SRV-22 电机发热（温升 ≥0.3 K/min 且温度跟着转矩 RMS 走）；
  冷/热机配对仍要两段波形，判据注明
- **配方**：事件流埋 `recipe_change`（C6 契约本来就定义了这个特征）→ SRV-27
  脉冲当量改写（配方边界处位移比例跳变 ≥5%）；不埋点则转介 SPC
- **驱动器参数**：`--drive-params drive_params.json`（current_loop_bandwidth_hz）
  → SRV-18：转矩谐振超出电流环带宽 ≥1× 判「电流环压不住」；
  C6 没有这个契约对象，走文件入口，数据来自驱动器手册/调试软件导出
- **扫频**：不新增文件——cmd 本身是 chirp/扫频即自动检测（相干 H1 估计）→
  SRV-19：实测闭环带宽 < 0.5×ωn 判 PI 失整定。
  **闭环扫频给不了开环相位裕度，结论只到「带宽实测 + 与 ωn 比值」，不冒充裕度**

至此 29 条判据里 28 条可评（SRV-27 需配方事件埋点，否则转介 SPC）。

### 3. `forensics` —— 设备日志根因分析 + 格式体检
> 对应需求：R-09、Q-09、R-04

```bat
mcopilot forensics analyze device.log --out out
mcopilot forensics probe  device.log --out out
```

**`analyze`**：日志时间轴重建 + 缺陷检出 + 带行号证据的根因候选排序。
检出的缺陷类型：定位偏差、轴参数被覆盖（换型竞态）、同轴时序竞争、通信丢包、到位时延超限、
标定残差漂移、节拍抖动、超时聚集、心跳断流、视觉不良率分段升高。

**每条结论都指回原始日志行号**，人可复核、可反驳；根因候选是假设不是结论，每条都附「怎么验证」。

**`probe`（格式体检）**：把「这套工具对你们的日志有多少耦合」变成**可量化的数字**，
分两层报：

- **第 1 层 行格式** —— 现有 `line_regex` 能匹配百分之几的行；不匹配就给一个可用的 `line_regex` 起点。
- **第 2 层 事件正则** —— 逐类事件的状态：
  - `已支持`（正则直接匹配）/ `需改正则`、`缺字段`（**这类事件确实在日志里**，写法对不上，改配置即可）
    / `未出现`（**这份日志没这类埋点**，对应检测器无数据可跑）。
- 最后给出两种**性质完全不同**的「跑不了」：**因格式跑不了**（改配置就能解决）vs **无埋点**（得改你们的日志埋点）。

样例 `samples/logs/` 里放了三份日志，让上面的数字可复算：
`machine_a.log`（内置格式）、`vendor_b.log`（**只换行布局、键名相同** → 适配成本 0，只改 1 处 `line_regex`）、
`legacy_c.log`（**键名也不同且缺一批埋点** → 指出 `target→pos`、`speed→spd` 这类对应关系，并点名哪些检测器会瘫）。

**`thresholds`（阈值灵敏度与误报边界）**：

```bat
mcopilot forensics thresholds logs/你的日志.log --out out
```

`knowledge/log_rules.json` 里的阈值是**通用起点**。现场标定最怕的不是「阈值不准」，
而是**「差一点点就翻车」**——阈值离结论翻转点太近，换一批数据结论就变了，你却以为是数据不同。

这个工具把每条阈值单独扫一遍，并用**二分法精确定位「结论翻转点」**（只做粗网格会把
「当前值离翻转点只有 5%」显示成「稳」）。顺带抓出两类**配置与代码不一致**：

- **死阈值**：配置里配了，取证代码**根本没读**（例：`concurrent_command_ms`）→ 现场调它不会有任何效果；
- **硬编码兜底**：代码用 `th.get("x", 默认值)` 读，但配置里没有这一项（例：`cycle_slow_ratio`）
  → 生效的是代码里的默认值，想标定只能改代码。

> 这两条不报出来，现场标定就是白调 —— 而且调的人不会发现。

附**检测器误报边界表**：每个检测器什么输入会误报、工具内置了什么防护、怎么人工复核
（写在 `knowledge/detector_meta.json`，知识与代码分开）。**工具只说「触发了」，不说「该不该信」**。

### 5. `motion` —— 运动参数离线验证
> 对应需求：R-04、Q-05、Q-06a

```bat
mcopilot motion plan --distance 100 --v 200 --a 1000 --j 5000 --freq 50 --damping 0.7 --tol 0.01
mcopilot motion gear --lead 10 --encoder 131072 --ratio 1 --ppr 16384 --configured 1638.4 --travel 200
mcopilot motion compare --distance 500 --v 200 --a 1000 --j 5000 --target 250 --counts-per-mm 13107.2 --exposure-us 50
mcopilot motion vectors --file out/golden_vectors.json    # 输出路径；out/ 是本地生成区，不入库
```

- 7 段 jerk 受限 S 曲线：分段、总时间、峰值、匀速段、制动距离。
- **跟随误差前置校验**：`e ≈ a / ωn²`，直接告诉你「这个加速度会不会吃掉我的定位公差」——
  不用上机试错就知道该把加速度降到多少。
  **前提**：type-2（位置环 + 速度前馈）；`a` 取恒加速度段的加速度（用峰值加速度算只是保守上界）；
  `ωn` 是等效闭环带宽对应的自然频率，不是机械固有频率。报告里会把这三条写在明面上。
- **电子齿轮/脉冲当量自检**：脉当量偏差 2.3% 在 200mm 行程上就是 4.7mm 定位误差。
- **黄金测试向量**：Python 算一遍、C# 再算一遍，对不上就是算法实现错了。

### 6. `cam` —— 电子凸轮表可行性校验与生成
> 对应需求：Q-05（电子凸轮）、R-03（雷赛/正运动/固高 SDK 封装）

```bat
mcopilot cam check samples\cam\pick_place_cam.csv --master-v 360 --master-a 200 --slave-v-max 300 --slave-a-max 2000 --slave-travel 120 --master-unit deg
mcopilot cam plan --master-travel 360 --slave-travel 8 --segments 4 --master-v 360 --slave-v-max 300 --slave-a-max 2000
mcopilot cam caps
```

- **段间速度阶跃（机械冲击的来源）**：凸轮表相邻两段斜率不同，从轴速度在断点处瞬间跳变。
  阶跃速度 `Δv = (kᵢ − kᵢ₋₁)·θ̇` —— **这是手画凸轮表最常见的致命伤**，
  表现是机台「咔哒」声 + 伺服跟随误差报警，而表本身看不出任何问题。
  报告直接给出「要消化这个阶跃、过渡段最少得多宽的主轴行程」。
- **从轴峰值速度 / 加速度预算**：斜率 × 主轴速度 = 从轴峰值速度；斜率 × 主轴加速度 = 从轴峰值加速度。
- **跟随误差预算**：`e ≈ a/ωn²`（type-2 前提），在定凸轮表时就把定位公差算掉。
- **凸轮表生成**：按梯形速度剖面分段，**段接缝处从轴速度归零**，所以段与段之间天然没有阶跃。
  生成后自动自检（主轴单调性、超限、阶跃、点数）。
- **三家能力差异（`cam caps`）**：这条是本工具最反直觉、也最有用的一条 ——
  **雷赛能整表从上位机下发（`dmc_cam_table_unit`），正运动只能引用控制器侧的表区间
  （`ZAux_Direct_Cam` 只传起止点），固高根本没有凸轮表**（gts.dll 导出表里 `cam` 符号 0 个，
  主从同步走「跟随段 + 事件交叉」）。
  **所以「换卡不改业务代码」在电子凸轮这一项上是假的** —— 跨品牌迁移时这一项不能平移。

> 这个智能体是 2026-10-20 补上的：复核需求基线来源时发现，原转写把「电子凸轮」写成了「电子齿轮」，
> 于是覆盖审计报「无覆盖缺口」，而基线明写的电子凸轮其实一个工具都没有。**转写错误会一路污染下游结论。**

### 7. `review` —— 实时运动代码规则评审
> 对应需求：R-10、Q-03、R-11

```bat
mcopilot review ..\MyApp\Source --out out
```

规则包（`knowledge/review_rules.json`）覆盖：阻塞等待、空 catch、无超时死循环、
**漏乘脉冲当量（轻量数据流检查）**、硬编码 IP、魔法数字、浮点等值比较、嵌套锁。

其中「漏乘脉冲当量」不是正则能抓的——工具会做一次轻量数据流：
识别哪些标识符喂给了 mm 制业务接口、哪些喂给了脉冲制 SDK 接口、哪些做过换算，
同一个变量同时落进前两者又不落进第三个，就是漏乘。**这正是「偶发定位偏差」最常见的根因。**

规则包可扩展：加一条正则就是一个新规则，团队把自己踩过的坑一条条沉淀进去。

### 8. `requirements` —— 工业需求基线与追溯
> 对应需求：全部

```bat
mcopilot requirements report --out out
```

逐条判定表 + 覆盖审计（**每条需求有没有工具兜住、每个工具有没有需求依据**——防工具自嗨）。

**需求基线的原文是转写来的，转写就会错，而错一处就污染一串结论。**
2026-10-20 把基线来源的 3 张招聘页截图放大 2 倍/4 倍逐条重核，抓出 11 处条目正文错误，其中两处是硬伤：

| 原转写 | 基线原文 | 后果 |
|---|---|---|
| Q-05「电子**齿轮**」 | Q-05「电子**凸轮**」 | 覆盖审计报「无覆盖缺口」，**而基线明写的电子凸轮一个工具都没有** —— 补了 `cam` 智能体 |
| R-03「固高/菁赛/正运动/…」 | R-03「固高/**雷赛**/正运动/…」 | 品牌清单里**少了做得最深的一家**，还多了一家基线根本没提的「菁赛」 |

同时恢复了 8 条被漏掉的限定语（如 R-11 的「专利、软著申报」、Q-07 的「（有源/无源对准）中至少两类」）。
**现在这条链路是闭环的**：`requirements_map.json` 的 `meta.provenance_check` 记录了核对方式与逐条差异，
`tests/test_knowledge_truth.py` 把「基线原文是什么」固化成断言 —— 以后谁再改 `requirements_map.json` / `cards.json`，
改错了会直接变红，而不是等到下一轮才发现覆盖审计在骗人。

覆盖审计现在会显式区分两种情况：**「所有 AI 承担度 > 0 且未登记缺点的需求条目都有对应工具」**
（真通过）与**「已登记的已知缺口」**（R-11 的专利/软著申报 —— 有 AI 可承担的部分，但目前没有工具承接，
如实登记为阶段 3，不再假装「无缺口」）。

### 电子书与代码同仓

`book/` 是电子书《取证式学习》——讲的是**怎么让每个技术主张都能被第三方当场核验**。
书原先照三个仓写成三册；随本仓开源时**只留与本仓代码对得上的那一册**——
判据是"**哪本的坐标能在这份代码里当场复核**"，不是"哪本好看"。
另两册的方法随各自的仓走：`axiscope` 与 `forensics-code-factory` 各自成书、各自同锚。
同仓之后一个 clone 就能拿到「书 + 一个可跑的案例仓」。

**书里的坐标锚在本仓自己**：`forensics-mcopilot@fdb8467`。
原先锚在发布前的工作副本 `mcopilot@b53ac62`——那个仓**不随本仓公开**，
读者手里没有它，坐标就只剩作者能核，而「当场可核」正是这本书要证伪的那件事。
旧锚点没有被抹掉，是**降级成历史**：停机点 `b53ac62` 仍是当时的真实事实，
只是坐标块指向读者拿得到的那份代码。

书里每个技术主张都锚在「仓库@commit + 路径 + 行号」上，而**引用会过期，过期的引用比没有引用更坏**，
所以有一道机器门禁：`python book\tools\check_doc_refs_heads.py`，
它逐条核对四个解析根里的文档引用并分八类报，**当前真断链 0** ✓。
（同级的 `axiscope` / `forensics-code-factory` 是独立仓，不随本仓发布；它们不在位时，
门禁把"所有仓都找不到"的路径归入**「缺仓不可判定」**而不是判成断链——
否则干净检出上 CI 第一次跑就是红的。八个分类里，只有「真断链」判失败。）
细节见 [`book/README.md`](book/README.md)。

### 架构契约

上面的目录结构**不是历史遗留，是设计决定**，并且被测试钉住（`tests/test_layout_contract.py`，10 项）：

| # | 不变式 | 架构理由 |
|---|---|---|
| 1 | `src/mcopilot/` 里**只有代码**，没有数据与文档 | 打包器只会带走包内的东西；真值基座与书要留在仓里当**被审证据** |
| 2 | `knowledge/`（真值基座）**在包外** | 它同时是运行时数据、被审证据（记厂商原件 sha256）、书里的锚点，还指向**仓外**的厂商原件——放进包里就把它降级成"随包的普通数据" |
| 3 | 仓库根的解析**不靠固定层数** | 写死 `parents[1]` 会在换布局或装成 wheel 时静默指错（曾把根指到 `site-packages`） |
| 4 | 在仓库根直接 `import mcopilot` **应当失败** | 否则你可能跑到一个装着的旧副本，而不是你以为在跑的那份——这正是 src 布局要买的东西 |
| 5 | 找不到真值基座时报**能照着做的错** | 分发单元是仓库不是 wheel，使用者遇到的第一件事就是"那我该怎么跑" |
| 6 | 声明的 **Python 下限要真的兑现** | `requires-python = ">=3.9"` 是一句对外承诺；`X \| Y`（PEP 604）这类 3.10 才有的写法一旦漏开 `from __future__ import annotations`，在 3.9 上就是**导入即报错**——本仓曾有一处漏开，已修并钉住 |

**分发单元是仓库，不是 wheel。** 真值基座与代码同仓、互为证据，且指向仓外的厂商原件，
装不进一个 wheel —— 所以支持的安装形态是**源码签出**或 **`pip install -e .`（可编辑安装）**。
`pip install .` 装出来的 wheel 不含真值基座：这是设计使然，命令会把这个事实和三条修复办法一起报出来。

```bat
pip install -e .                    REM 受支持的安装形态（可编辑安装）
mcopilot all --out out              REM 装完直接可用
```

python scripts\verify_bilingual_parity.py          REM 双语同步门禁：两份 README 结构是否一一对应

> 后五个 `verify_*.py` 是**审的工具**：它们只用标准库、不 import mcopilot 的业务函数 ——
> 拿被审的代码验被审的结论，就是 axiscope 审计里点名的「同源自证」。

**真值桥**（`verify_traekb_citations.py`）解决的是一个更隐蔽的问题：
Trae 代码工厂的知识库 `gen/adapters_kb.js` 是**手抄**的官方真值 ——
`chk: '官方原型 GT_Open(...)（gts.csv:326 / gts_hdr.csv:398）'` 里的行号只是散文，
生成器从不读真值 CSV。真值一改，引用就悄悄过期，而**过期的引用比没有引用更坏**
（读的人以为出处仍然可信）。这个脚本把每条 `file:line` 引用变成可执行断言：
该行必须**真的含有它所声称的那个符号**。它已经抓出过一处真问题 ——
固高回零 mode 只列了 4 个，把官方表里 `HOME_MODE_LIMIT_HOME(11)`、
`HOME_MODE_LIMIT_INDEX(12)`、`HOME_MODE_LIMIT_HOME_INDEX(13)`、
`HOME_MODE_FORCED_HOME(40)`、`HOME_MODE_FORCED_HOME_INDEX(41)` 藏住了
（后两个还在原引用范围 163-169 之外）；现已补全为 163-171 全表 9 个 mode。
这条桥由 `tests/test_trae_truth_bridge.py` 常驻看守。

`compile_check.ps1` 做三件事，**任一失败即退出码 1**：

1. 编译适配器（接口 + 仿真器 + 雷赛 + 正运动 + **固高**）→ `Motion.dll`；
2. 编译契约测试（配 `scripts/xunit_shim.cs` 最小替身，只查语法 —— 物理断言要插卡才跑）；
3. **编译并运行** `MotionSelfCheck.cs`：验证仿真器真的模拟出了跟随误差、指令与反馈同口径、异常路径真的会抛。

> 第 3 步是这轮加的。它当场抓出了两个真 bug：短距（三角形）工况下速度没夹紧导致反馈算成 0，
> 以及 `AdvanceUntilDone` 永远不会把轴置为完成。**只编译不运行，这些 bug 一个都跑不出来。**

> ⚠ C# 源码一律写成 **UTF-8 with BOM**：csc / MSBuild 对无 BOM 的源文件按系统 ANSI 码页（中文 Windows 是 GBK）读，
> 中文注释和字符串会被解码坏，表现为一堆看不懂的语法错误。生成器已强制这一点，编译脚本也加了 `/codepage:65001`。

## 七、这套东西的边界（请认真读）

1. **它不会替你调伺服。** 惯量辨识、增益整定、共振规避必须上机 + 示波器。
   它能做的是**离线波形诊断**（读波形 → 反推等效参数 → 候选根因），以及整定前的预算校验。
2. **估出来的是等效参数，不是物理真值** —— 但要说清「估算」到底指哪一项：
   - **跟随误差是实测值，不是估算。** 有编码器的轴上它直接来自编码器计数 /
     驱动器 `0x6064`（正运动 MPOS、雷赛 `dmc_get_encoder` 独立计数通道）。
     真正的风险不是「估不准」，而是「**该轴根本没有反馈通道**」——
     这个不由工具猜：适配层用 `HasRealFeedback(axis)` 如实声明，契约测试按它分流（见第 9 条）。
   - **被估算的是伺服的等效二阶参数（ωn/ζ）** ≈ 闭环带宽，**不是机械固有频率**。
     高阶响应下与真实 -3dB 带宽的偏差实测可达数十个百分点，判断共振必须再做扫频。
3. **`e ≈ a/ωn²` 有前提。** type-2 + 恒加速度段。不满足时报告里会写明，
   工具不会拿阶跃瞬间的误差冒充稳态跟随误差。
4. **它不猜厂商行为，而且现在有了外部真值兜底。**
   - 能力矩阵每条都带 `verified` 口径：`official-manual`（官方手册）/ `official-binding`（官方 C# 绑定）/
     `public-doc`（公开资料）/ `needs-manual-check`（必须厂商给）。
   - 雷赛/正运动的**每条 P/Invoke 都与官方 C# 绑定逐行校验**（函数名 / DLL 名 / 参数个数），回归测试常驻；
     **雷赛再往下钉了两层**：与官方 C 头文件 `LTDMC.h` 的原型逐条对（**含返回类型** ——
     `long` 15 条 / `DWORD` 11 条 / `double` 2 条不是 `short`，写错就按错的宽度读返回值）、
     与**手册附录 11《运动控制函数索引》**的 169 条逐条对（函数名 → 章节 → 页码）。
     错误码全表、停止原因全表、回零 mode 0~12、`dmc_vmove` 方向、圆弧参数序、SDO 入口等均来自官方手册原文。
   - **固高现在也是「官方绑定级」**（2026-10-20 拿到官网 SDK 包）：34 条 P/Invoke 逐条对过官方 `gts.cs`
     （函数名 / 参数个数 / 参数类型 / ref-out 修饰）、对过官方 `gts.h` 的 C 原型、
     对过 3 个结构体的**字段顺序与字节偏移**（`gts_structs.csv`）与 200 个官方宏的枚举值
     （`gts_hdr_macros.csv`）；调用约定取自 `gts.h` 的 `#define GT_API extern "C" short __stdcall`。
     手册级的两件真值仍在（`gts_manual_index.csv` 167 条指令索引 + `gts_prototypes.csv` 34 条原型带页码），
     现在是**第四道**防线：函数名既要在官方绑定里、也要在手册索引里。
     固高**没有** `SetPulsePerMm`（当量是 `GT_ProfileScale` 的分数比且公式未公开）→ 适配器**不下发**当量变换，
     要求控制器保持默认 1:1 当量，脉冲当量由现场提供、软件侧换算。
     固高也**没有厂商停止原因码** → 适配器的停止原因是**本工具按状态字位推导的自定义编码**，已写明。
   - **再钉一层 DLL 导出表**（`knowledge/sdks/official_api/dll_exports.csv`）：官方 C# 绑定里**声明了**、
     官方 C 头文件里**也声明了**，随包 DLL 却**没导出**的函数，照抄一样 `EntryPointNotFound`。
     实测命中两例：`ZAux_Direct_GetNtype`（官方 `Zmcaux.cs` 有、`zauxdll2.h` 有，**64 位 `zauxdll.dll` 导出表里没有**）、
     `GT_GantryHoming`（官方固高 `gts.cs` 有、**4 个 `gts.dll` 导出表里都没有**）。
     雷赛 32/64 位 `LTDMC.dll` 的导出集合**并不相同**（32 位少 8 个函数）—— 而目标进程位数还没定，
     所以回归测试要求**手上有哪个位数就必须在哪个位数里导得出**。
     固高这边多一层：SDK 包里有 **5 个同名 `gts.dll`**（4 个 SDK 的导出表相同，各 782 个符号；
     `03_Demo工具_MCT2008/` 那份旧的只有 569 个、**少 214 个**）→ 拷错不立刻崩但会缺一整套功能，
     回归测试按「变体」列区分，notes 里写明只拷 `02_CSharp封装/<位数>_single_card/` 那份。
   - **因此「用你们型号的函数手册复核」现在只适用于「按批次/型号才确定」的那几项**：
     现场卡型号与接线盒、IO 端子表、CMP 通道↔端子、总线从站 PDO 映射、SDK 版本↔固件。
     这几项已列成**可直接转发**的清单（`docs/厂商手册索取清单.md`），拿到答复前**显式抛异常**，不给「看起来能用」的实现。
5. **它只做离线分析。** 所有工具都不连真机、不下运动指令；真机验证由人做。
6. **根因候选是假设。** 每条都附「怎么验证」，证伪了就换下一条，不要直接当结论用。
7. **样例与规则同源，这一点不回避。** 样例日志由 `make_samples.py` 按同一套约定生成，
   所以「样例全检出」**只证明检测逻辑自洽，不证明对你们的日志有效**。
   `forensics probe` 就是为了量化后者。
8. **阈值要按你们的产线调——但要把「依赖真数据」和「不依赖真数据」分开看。**
   - **不依赖真数据、已定死**：厂商语义（错误码 / 停止原因 / 方向编码 / 单位口径 / 回零 mode）来自官方手册与官方绑定。
   **依赖真数据**：数值门限（跟随误差多少算异常、节拍抖动多少算异常、丢包率）与你们日志的键名映射。
   - **还能再收敛的两步**（不需要真机就能做）：① 把固定门限改成「基线 + MAD」的相对判据，对不同产线更鲁棒；
     ② 给每条阈值做**灵敏度分析**，标出「结论翻转区间」，现场标定时优先标定脆阈值。
   - **第 ② 步已经做了**：`mcopilot forensics thresholds` 用二分法精确定位每条阈值的「结论翻转点」，
     标出**哪些脆**（离翻转点近，优先标定）、**哪些偏严**（当前值永远不命中 → 检测器是哑的，
     不是「没问题」）、**哪些配置根本没生效**（死阈值 / 硬编码兜底，调了等于没调）。
     粗网格会骗人 —— 它会把「离翻转点只有 5%」显示成「稳」，所以必须二分。
   - **剩下的仍然必须用真实数据**：相对判据的基线要你们的正常段分布，最终定在哪个数要你们的故障分布。
     **本工具给不出来，也不该猜。**
9. **仿真器自检只证明自洽，不证明真机通过。** `MotionSelfCheck.cs` 跑通说明「仿真器与契约断言口径一致」，
   说明不了「你们的卡插上去也一致」。真机一致性由 `MotionContractTests` 在插卡后验证，
   其中两条是专门抓「看起来能跑、实际会出事」的：**跟随误差必须非零**（抓反馈位置是假数据）、
   **点动方向必须与速度符号一致**（抓方向编码写反 —— 雷赛 0/1、正运动 −1/1，两种编码都容易抄反，
   写反了不报错、轴直接往反方向跑）。
   ⚠ 这两条都会先看 `HasRealFeedback(axis)`：**开环轴上跟随误差必然恒为 0**（正运动 ATYPE=1/7 的 MPOS 只是
   DPOS 的副本；雷赛没接编码器时 `dmc_get_encoder` 恒为 0）—— 那不是假反馈，是没有反馈通道。
   适配器必须如实声明，否则真机上只会得到一条误报。
   厂商语义（方向/停止方式/IO 电平）与物理接线（位号/端子）**仿真覆盖不了**，
   这部分走 `docs/首次上机验证清单.md` 的分级上机与 `docs/厂商手册索取清单.md` 的厂商确认。
10. **能力矩阵没有假装覆盖全。** 需求基线覆盖 6 个品牌，目前有**官方一手件可核对**的 3 个（雷赛 / 正运动 / 固高），
    其余 3 个列在「待录入品牌」里，原因各不相同（不是偷懒，是一手件到不到手决定的）：
    - **ACS**：形态不同（SA/SA-LT 是独立整机，**没有卡驱动可 P/Invoke**），要先把「通信库分支」这条架构路线定下来。
    - **软赢 / 高川**：连公开一手件都不足，建出来只能是猜的。
    - **更正（2026-10-20）**：「菁赛」**根本不在需求基线的品牌清单里** —— 复核基线来源后确认，
      R-03 原文是「固高、**雷赛**、正运动、软赢、高川、ACS」，早先转写把「雷赛」误读成了「菁赛」，
      于是**做得最深的那一家反而被排除在品牌清单之外**。
      现在 `cards.json` 的 `brands_in_scope` = 固高 / 雷赛 / 正运动 / 软赢 / 高川 / ACS，
      「菁赛」移入 `out_of_scope_brands` 并写明为什么不投入 —— 不悄悄删，留个账。
    - **固高已进矩阵，且是官方绑定级**：官方 SDK 包（`gts.h` + `gts.cs` + 4 个 `gts.dll` + 14 本手册）已在手，
      34 条绑定逐条对过官方 C# 绑定与 C 头文件、三层真值（绑定 / 头文件 / DLL 导出表）全绿，
      `verified` 已从 `needs-manual-check` 升为 `official-binding`。
      仍须厂商确认的只剩三项：**当量变换公式**（手册只给取值范围与 `|alpha|>|beta|`，没给公式与方向）、
      **现场实际型号与固件版本**（PG=脉冲量输出 / PV=模拟量或脉冲量输出，端子板另有 `GT2-400-ACC2-VB-G/-V`）、
      **GEN 的 SDK 包**（`GTN_` 一个符号都不在 GTS 包里）。
      顺带查实了一件事：**固高至少两条产品线，且 SDK 包是分开的** —— GTS 用 `GT_` 前缀（PCIe 插卡），
      GEN 用 `GTN_` 前缀且**首参是控制器编号**（两族签名不能互换）；
      官方 GTS SDK 包里 `GTN_` 符号**一个都没有**（`gts.h` 535 条声明 / `gts.cs` 473 条声明 / 5 个 DLL 的导出表全查过），
      GEN 是独立产品线（自带用户手册与基本功能手册），**它例程里的 `#include "gts.h"` 只是同名文件**。
      → **要接 GEN 必须单独要 GEN 的 SDK 包**。这仍是那句教训：**别凭前缀下结论**（雷赛 `nmc_`/`dmc_` 就是同库不同前缀）。
    **PDO 字节级映射仍须厂商确认**（错误码全表与停止原因全表已由手册定死，不再需要问）；
    **固高与雷赛的 IO 端子表都已由官方用户手册抄全**（固高 121 行 `gts_io_terminals.csv`、
    雷赛 88 行 `leisai_io_terminals.csv` + 表 8.3 位图 + 1.4 配套表 + **总线卡 DMC-E 附录 1 的 72 行
    `leisai_dmce_terminals.csv`**），不再需要问。
11. **产品形态决定实现路线，接新品牌先问形态。** 插卡 = 板卡驱动 P/Invoke（雷赛 `LTDMC.dll`、固高 `gts.dll`）；

    雷赛内部的分界是「卡（DMC / DMC-E 插卡）/ 控制器（EMC / MC / PAC 整机）」，
